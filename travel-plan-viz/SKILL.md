# 旅行计划可视化

把一趟旅行变成单文件 HTML 页面：交互地图、每日时间轴、出发前订票提醒。机械逻辑用自带引擎（`assets/map.js`、`assets/reminders.js`），美学交给设计步骤（`frontend-design` / `huashu-design`，或内置准则兜底）。

## 第一步：判断模式

- 用户**只给了目的地+天数**（如"香港 4 天 3 晚"）→ 模式 A（从零规划）。
- 用户**已提供行程**（文字或旧 HTML 文件）→ 模式 B（解析已有计划）。

## 模式 A：从零规划

### 第 1 步：需求澄清（只问与目的地无关的硬信息）

用户常只给目的地（如"目的地东京"），缺以下任何一项先补问——**一轮问完、用对话文字问**（别依赖平台特有的表单/选择组件，可移植性差）；用户答"你定/都行"的按括号默认走，并在方案里说明用了默认值：

- **天数**（如"4 天 3 晚"；用户**不确定也没关系**——先跳过，等第 3 步景点对齐后按确认的景点倒推推荐时长。问就只问开放数字，**别附自己估算的天数档位或"推荐几天"**——摸底完成前你并不知道该地值得几天，判断权在用户）
- **出发日期**（未定则按"约 30 天后"估算：trip 写 `dateTBD: true` + 估算日，提醒照算但须告知是估算、定档后把 HTML 丢回来重算）
- **出发城市**（航班建议班次必需——没有它 flights 区写不了；用户没给就问，别猜）
- **用户旅行史/偏好只认用户口径**（2026-08-26 拍板）：`samples/` 里的历史行程是本 skill 的**产物演示**，不是用户的旅行记录或偏好画像——行程里没排过 ≠ 用户没去过/不喜欢，**别从样例推断"用户去过/没去过哪里"，拿不准就直接问**
- **当地交通方式**（自驾/租车 / 包车 / 公共交通——决定排程半径；大城市缺省公共交通，地广景散的地区如晋东南/黔东南必问）
- **同行构成**（一个人 / 情侣朋友 / 带孩子·几岁 / 带长辈——影响乐园取舍、餐厅、酒店房型与每日节奏）
- **偏好用开放式问**："有特别想看的吗？有明确不想去的吗？"——**不预设目的地的主题选项**。目的地有哪几条主题线，是第 2 步摸底后才掌握的事实，别拿模型记忆当选项拍给用户。

### 第 2 步：目的地摸底（先知道"有什么"，才能谈"想去哪"）

目的：拿一份**新鲜的原始景点池**。后续清单只能从这个池子里出——**模型记忆里的景点名单不算数**（可能过时、可能记错、更感知不到当下热度）：

- 配置了 `tools/xhs_research.py` 就先抓「<目的地> 攻略」社区笔记（边界见 research-guide「本地可选工具」节）。
- 再用联网搜索补齐："<城市> 必去景点 攻略"、"小红书 <目的地> 攻略"（工具不可用时，站内笔记基本搜不到——2026-08-23 实测小红书内容不进通用搜索引擎，降级走 research-guide「网友实测情报挖掘」信源降级链）、官方文旅号/景区官网，**以及全国重点文物保护单位/世界遗产名录——文保等级是后续排序的第一权重，摸底阶段就把权威名录拉进池子**。**国保与世遗必须逐条纳入考虑：可以优先级不高，但不能遗漏（2026-08-21 拍板，无条件适用于任何行程）**。名录要**落到县**——把行程走廊穿越的每个县逐一拉县域国保名录（境外/无国保概念的目的地对照世遗名录），第六批以后（尤其第七/八批）乡野国保单独过一遍——它们在"必去/攻略"类热度内容里永远不会出现，只有名录枚举能捞出（实测踩坑：布村玉皇庙与法兴寺同镇顺路、礼义三庙恰在北留→王莽岭走廊上，均因只做热度检索而漏网）。第 3 步清单对齐时，走廊上的国保/世遗**逐条给入选/排除结论**——排除理由可轻（绕路、锁门、与主题无关），但不可不表态；值得备选的进当日 alternatives。别让"没看见"伪装成"权衡过"。
- 摸底产出：候选景点池（名称 + 为什么去 + 大致区位），**此时不筛不排**；发现某景点停业/整修等硬信息一并记下。

### 第 3 步：景点清单对齐（先对齐"去哪儿、去几天"，再排"怎么排"）

排逐日方案**之前**，先给一份**按推荐顺序排列**的候选景点清单，把取舍权交给用户：

- 清单要有主见：按推荐顺序排——**文保等级/世界遗产是重要客观权重**（国保批次、世遗名录是国家级权威背书，客观稳定；含金量高的——整条国保带、世遗、国宝级彩塑——要显著上浮，该进第一梯队就进第一梯队），与经典程度、同行构成适配、地理顺路、季节时令**综合排序**：既别因"没文保分"把自然经典机械压底，也别唯文保论。通常 8–12 条；每条带一句话理由、文保牌面（如有）、适配人群（带娃/长辈友好、需暴走等）、参考时长、门票档位，并区分**默认入选**（约 天数 × 2–3 个主景点）与**备选**。**每条都必须出自第 2 步摸底池**；用户点名池外景点时，先补查再上清单。聚合类条目（如"古建线"）要把摸底到的子项**列全或列代表+数量**——压缩排版时把整个子集丢掉，等于摸底白做（实测踩坑：浊漳河谷整条线被"悟空线"条目折叠丢失）。
- **演出/情景剧默认不入主线**（2026-08-22 拍板）：《又见平遥》《如梦晋阳》类驻场演艺是商业演出，不是文保/景观本体——清单**默认入选不含它们**，场次/票价可作当日贴士参考信息，但**仅在用户点名时排入主线**；别替用户把「看场演出」当必选单元，更别与住宿选择或当日排程硬绑定。
- 请用户明确回复（三选一 + 可补充）：**全都要 / 删掉某几个 / 把某个景点提级**（提级 = 排进当天核心时段并给足时长，其他点为其让路）。
- **清单交付的那一轮不夹带天数/线路组合**：请用户取舍（上一条三选一）就到此为止，别顺手拍出「组合①②③+各自天数+推荐标」让用户挑——那是替用户做了天数判断（实测踩坑：西班牙案例第一轮拍主题线+天数推荐、被纠后又在清单同轮打包组合，两轮都被打回）。倒推天数只发生在用户取舍完成之后（见下一条）。
- 用户回"都要 / 你定"→ 按默认顺序进下一步；有删改提级 → 先更新清单再继续。**不替用户做取舍决定，但也绝不甩一个无序大列表让人自己消化。**
- **若第 1 步天数未定**：清单不按天数裁剪（全量按推荐顺序给出）；用户取舍完成后，按确认清单**倒推推荐时长**——按片区聚类估游览单元（同类小点合计半天、大点/乐园一整天、近郊一日游 1 天），再叠加抵达日与返程日缓冲（各至少半天），给出"**建议 X 天 Y 晚**"+一句测算依据；用户认可或增减天数后，才进第 4 步。

### 第 4 步：逐日方案

**先查航班再排程**（时机刻意靠后：整体清单与天数对齐之后、具体每日行程之前——清单未定不空查；出发日期未定则顺延到「调研补全」）：按 research-guide「航班」节给 3-5 个建议班次（已装飞猪 skill、`tools/flight_research.py` 或零 Key 的 `tools/gflights_research.py` 查实时价，结果标来源+时间戳；无渠道给参考区间），用抵达/离开时刻约束首尾两天的排程（机场/车站往返交通耗时一并计入）——别排好行程再硬凑航班。

只用对齐后的清单，在对话里用 markdown 提出详实逐日计划（早/中/晚、景点、交通、住宿）；被提级的景点放当天黄金时段（通常是上午首个或日落场）。**每天标注当晚住宿的大体区域**（城区/镇名即可，返程日无住宿则不标），当日车程链终于「→当晚住宿」段——住宿是排程的一环，不是链条外的备注；链条里每个浏览型点位名后附大概浏览时长（如「主教座堂（浏览约2小时）」，与当日 slot 的 time 字段一致）——只有车程没有浏览时长的链条会让人误判当天装不装得下。排程守安全硬约束：**天黑不走山路**（日落后只走高速/国道/少量平原省道，当日首尾山路段对照日落时刻核验，细则见 research-guide「点到点交通」节）。

### 第 5 步：迭代与确认

与用户来回迭代，直到明确确认；确认后进入「调研补全 + 生成」。

**每轮整体优化后，汇报「舍弃点位 Top10」**：把当前未入选的候选（被换出的、枚举后排除的、备选未转正的）按含金量排序取前十，逐条带**当初舍弃原因**与**翻案代价**——取舍要留痕。排除理由会随线路改版失效（实测：定林寺/清梦观/晋城二仙庙的「绕路」理由在 D4 改线后反转为顺路，靠这份复盘才捞回），这份清单是唯一的重捞机制（2026-08-21 拍板⑧）。

## 模式 B：已有计划

1. 解析用户给的行程。**若是本 skill 生成的旧 HTML**：直接解析其中 `<script id="trip-data" type="application/json">` 的完整 `trip` JSON（数据与呈现分离，别去反解析渲染后的 DOM——必丢字段）；旧版页面没有这块时才从 DOM/文本提取。
2. **顺手提建议（Agent 增值，但别硬来）**：把用户的计划对照"完善行程"的维度（行前须知/天气应对、提前订票项、点到点交通、节奏与缓冲、当地必吃、片区住宿是否合理等）快速体检，在**对话里**给**最多 3–4 条**具体、可选的优化建议。原则：
   - 只挑**真实存在的缺口**；计划本就完整就直说"挺完整"，**不要硬凑、不要说教、不要替用户重排行程**。
   - 一句点出问题 + 一句给方向即可，简洁；建议默认口头给，保持 HTML 成品干净（用户想把建议也放进页面再加）。
   - 这是我们区别于"纯提示词转 HTML"的地方——发挥 Agent 的判断力，但点到为止。
3. 进入"调研补全 + 生成"（生成不被建议阻塞；采纳哪些由用户定）。

## 调研补全 + 生成

1. **先判断第三方 skill 适配**（详见 `references/research-guide.md`「第三方 skill 适配」节）：若当前 Agent 可调用用户**已装**的官方旅行 skill / MCP（飞猪、高德、腾讯地图、滴滴等），**优先用它们拿对应数据**——高德地理编码拿精确坐标（**注意：高德/腾讯返回 GCJ-02 坐标，写入 `trip` 前必须用 `map.js` 的 `gcj02ToWgs84` 转成 WGS-84**，否则在 OSM 地图上偏移几百米）、路线规划增强点到点交通、天气查询、生成专属地图/导航/叫车的行动链接；飞猪拿实时航班/酒店/门票及预订链接。把用到的来源登记进 `trip.dataSources`，行动链接写入对应节点的 `actionLink`（**链接只用官方返回的，绝不手拼**）。**没有这些 skill 就全部走下面的静态调研**，成品不缺区块。数据实时性/真实性由对方官方 skill 负责，本 skill 不背书、措辞中性。
2. 按 `references/research-guide.md` 联网补全（官方 skill 未覆盖的部分）：坐标、评分、点评、营业时间/休息日、门票参考价、需提前订项及 `leadDays`；**行前须知**（天气/台风/穿搭/支付/App/购票时机）、**点到点交通**（**任何交通方式都须逐段交通链**——住宿点→首站→景点间→末站→住宿点，每段方式+耗时，自驾/包车加距离、公共交通加票价，起点为前一晚住宿点；**天黑不走山路**：日落后只走高速/国道/少量平原省道，首尾山路段按日落时刻核验，见 research-guide「点到点交通」节）、**时令限定活动**、每餐**必点菜+参考价**；航班给 3-5 个**建议班次**、酒店按**片区+价位**推荐（**连锁品牌优先**——华住会/首旅如家/锦江等系，连锁未进驻处如实降级本地口碑款并注明；**实时价仅定档后查**——dateTBD 期间只给参考区间，定档重算时经官方渠道回填，见 research-guide「酒店」节；**每片区核一个城区级锚点坐标**（lat/lng 成对、WGS-84），并给每日 `stayArea`——当天住宿的大体区域，写进 `days[].stayArea`，页面据此在当日头部标注并在地图画 🏨 锚点）、并准备**免责声明**与全程**贴士**。**图片只做批量存在性摸底（一次 imageinfo API），逐 URL 的 200 校验放到生成之后按优先级补——图片不阻塞正文**（见第 8 步）。排程体现**天气/季节逻辑**（户外排凉爽时段）。航班若未在第 4 步查过（如当时日期未定），在此按 research-guide「航班」节补查**建议班次**——价格渠道不限（飞猪 skill / `tools/flight_research.py` / `tools/gflights_research.py`（零 Key）/ 飞常准 MCP / 联网搜 OTA 页面），结果标来源+查询时间戳，**页面声明「机票价格仅作参考、以订票页为准」**。若本机配置了可选工具 `tools/xhs_research.py`，可按 research-guide「本地可选工具」节先抓小红书攻略作定性参考（边界照该节执行）。另有四件必做（2026-08-23 拍板，细则见 research-guide 对应节）：**①联票/城市卡/年卡**——排完行程主动查并做回本数学，不划算也如实写"算过、不值"；**②开放限制写进景点详情**——闭馆日/仅周日短开/免费时段限制写入 slot `openingHours`/`closedDays`，即使当日排程已避开；**③境外交通**——每城查交通卡/次票/机场线补价写 `preTrip.transitCards`，交通链避免出租车（公交/地铁/步行/铁路优先，打车仅兜底并标参考价）；**④境外住宿**——酒店片区补「网友推荐（主要小红书）」写 `hotelAreas[].crowdPicks`，价格带实付年份、渲染非实时脚注。
3. 组织成 `assets/page-contract.md` 里定义的 `trip` 数据结构（含可选的 `dataSources` 与节点 `actionLink`）。
4. 用**设计步骤**生成风格化 HTML：**优先**调用专业设计 skill——`frontend-design` 或 `huashu-design`（花叔Design），任一已安装即用；**两者都没有**时，按 `references/design-guidelines.md` 的内置美学准则自己出。无论哪种方式都要严格遵守 `assets/page-contract.md` 的区块与约束：
   - **可套骨架模板 `assets/page-template.html`**（从已发布样例蒸馏）：把完整 trip JSON 与两段引擎（`assets/map.js`、`assets/reminders.js`）注入占位符即出页，再换配色/主题词（组装说明见模板文件头注释）；设计 skill 整体重设计时无须套模板——两条路线都要过第 6 步机械校验。
   - 内联 `assets/map.js`、`assets/reminders.js` 内容到 HTML（保证单文件）。
   - 完整 `trip` 对象以 `<script id="trip-data" type="application/json">` 内嵌进页面（后续迭代修改的数据源）。
   - 页顶清单用 `computeReminders` + `renderChecklistHTML`。
   - 展示行前须知区块；航班区展示建议班次（已预订的高亮），酒店按片区+价位展示，附近显著展示免责声明。
   - 时间轴卡片展示营业时间/门票参考价/交通/时令活动等可选字段；展示每日餐饮（必点菜+价）、当日与全程贴士、单日二选一方案（若有）；**当日有 `stayArea` 时在头部显著标注当晚住宿片区**（返程日无则不标）；**境内行程**在当日头部加「📍 高德打开当日点位」链接——用 `buildAmapDayMarkersLinks(当日 slots 坐标 + 当晚住宿锚点)` 生成（单链接上限 10 点、超出自动分块），并如实注明：高德路书无公开创建接口，此为官方免 key 多点标注 URI（进高德后是带名称的点集合、无连线，收藏/存路书须在高德内手动操作）；境外行程不加。
   - 地图用 `initTravelMap`，引入 Leaflet CDN 的 CSS/JS；`hotelAreas` 带锚点坐标时以 `{ stays }` 传入画 🏨 住宿锚点。
   - 时间轴上 `needsBooking` 项插入 `reminderBadgeHTML(leadDays)`。
   - **可选适配元素**：节点带 `actionLink` 时渲染「去预订/导航/叫车」按钮（缺则不渲染、不手拼）；`dataSources` 非空时中性注明数据来源。
   - 每趟行程用不同配色。
5. 保存为 `<行程名>-旅行计划.html` 到工作目录。**攻略正文优先**：正文数据（坐标/时刻/票价/天气/酒店/餐饮）齐了就生成并交付，不等图片逐点校验完成——**可先出无图版**（`photo` 字段省略或留空，页面按 page-contract 的统一降级呈现，不露破图）。
6. **机械校验（必做）**：跑 `node <skill目录>/assets/validate.js <生成的.html>`——校验 trip 必填字段、坐标越界/离群、必需区块标记、trip-data 内嵌。有 ERROR 必须修复后重跑至通过；WARNING 逐条人工判断。
7. 告诉用户：之后可把该 HTML 文件丢回来，说"把第三天的 X 挪到第四天"，会在原结构上修改（直接改内嵌的 trip-data JSON 再重渲染）。若生成时 `dateTBD` 为 true，**定档丢回重算**还包含：按真实日期重算提醒、补查此前顺延的航班，以及**逐片区补查酒店实时价**（经官方渠道，时机细则见 research-guide「酒店」节）。
8. **图片按景点优先级后补**（2026-08-21 拍板，正文交付后进行，不倒挂）：按优先级逐点找图并 200 校验——优先级：门面/顶流 → 行程核心/国保孤本 → 古镇古堡 → 自然/长尾；每点 1–2 张即可、宁缺毋滥，无图就留空走降级，**别为长尾图拖着正文不交付**。过审 URL 填进对应 slot 的 `photo` 字段重渲染出带图版。Commons 礼貌抓取细则（批量 imageinfo 摸底、逐 URL ≥8s 间隔、同景区通用图如实标注）见 research-guide「图片按优先级后补」节。
